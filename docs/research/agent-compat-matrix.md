# Alan's Way: Hermes, Grok Bot and conditional Duet compatibility

Research date: **2026-10-27**, revised against Alex's authoritative seven core features. Targets: **stock production Hermes and Grok Bot**, with **Claude Duet conditional**. Recommendation: **go-with-changes** for the shared tool architecture; **full seven-feature product readiness is UNVERIFIED**. Preserve the agents and add tools, configuration and profiles; do not fork them. Codex is the requested computer-use performance yardstick, not a target client.

## Scope and evidence

Source snapshots: `alans-way-agents` at [`4da7c64bcf11fec0c10c1cddc569ec125a93a032`](https://github.com/capthvnsen/alans-way-agents/tree/4da7c64bcf11fec0c10c1cddc569ec125a93a032), and a separate temporary, read-only clone of `alans-way` at [`7e05d521c2a2f9add46423e39a4b27d6e67049e3`](https://github.com/capthvnsen/alans-way/tree/7e05d521c2a2f9add46423e39a4b27d6e67049e3). Repository citations below pin file paths and line ranges to these snapshots. Official online documentation was searched and read; its behavior can change after this date. **UNVERIFIED** means the inspected primary sources do not establish the claim or the necessary live-client behavior was not tested. An undocumented limit is not an unlimited allowance.

This is research only: no client was configured, no real desktop was driven, no secrets or private profile files were read, and no application code, configuration, tests, or CI were changed. The only repository change is this report.

“One server” should mean **one implementation and tool contract**, with authenticated per-bot sessions. It need not mean one process for all agents: today's bridge starts one router child per MCP session using the bridge's fixed bot arguments. Multiple sessions on one bridge therefore do **not** automatically become distinct bot identities. [A2]

### Grok API is a separate integration

The xAI **Remote MCP API** documents Streamable HTTP and SSE, **not stdio**, with caller-provided `authorization`, extra `headers`, and `allowed_tools`. `require_approval` and `connector_id` are unsupported. These facts must not be transferred to Grok Bot's product client; they describe the API, not Bot connector compatibility; a replacement API harness is outside the stock-agent scope. API-specific MCP image results, elicitation, numeric count/size caps and MCP timeout guarantees remain **UNVERIFIED**. [G6]

### Deferred CLI clients

Claude Code and Codex are **out of scope as targets**. If later justified, support them only through a thin CLI wrapper using the same MCP tools over Tailscale; no agent fork, separate driver or replacement chat runtime. This report does not assess their compatibility further.

## Tailscale backbone: confirmed for owned infrastructure, challenged at hosted ingress

**Confirm:** retain Tailscale as the Mac–VM and device–VM backbone. The sibling repo requires it and `connect-mac.sh` validates tailnet destinations and restricts the VM's SSH key by tailnet source ranges. Keep the Mac's app API loopback-only; invoke its connector through SSH on the tailnet. MCP stdio/HTTP and noVNC WebSockets are application transports riding that network, not substitutes for it. [W9, W10]

**Challenge “everything” literally:** Telegram and vendor app/model traffic use their providers' services, not an Alan's Way-controlled tailnet. Grok remote URL MCP is called from Cursor's servers; putting its cloud computer on Tailscale does not put those connector servers on the tailnet. Official Bot docs mention private-server approval, but do not establish private tailnet routing for URL connectors. **UNVERIFIED:** private URL reachability from Alex's actual Grok plan/account. [G1, G8]

Two materially different choices, both using stock agent extension paths:

- **Strict private tailnet:** prefer a command-based connector on an authenticated tailnet member calling the VM router over restricted SSH, or HTTP via private Tailscale Serve. Grok Enterprise documents Team Setup Scripts installing Tailscale on hosted computers; its exercised pattern uses an exit node, with subnet routing requiring a pilot. This is evidence for computer networking, **not** remote URL connector networking. Other-plan support, command-MCP private egress, persistence and outbound SSH still need a live check; the repo recorded SSH blocked on Oct 26. Do not route through Alex's laptop as the sole gateway when lid-close continuity is required. [G9, T1, W1]
- **Hosted HTTPS ingress:** Tailscale Funnel can expose an authenticated VM-side MCP endpoint to non-tailnet clients. That retains Tailscale infrastructure but adds **public internet ingress**; it does not satisfy “private tailnet only.” Keep the local Mac API and VNC viewer private. Current bridge auth is bearer-only and client header support must be verified; Funnel also has non-configurable bandwidth limits, so do not assume a high-performance screenshot path. This option needs an explicit product decision, not a silent fallback. [T2, A2]

For Duet, direct tailnet membership/command-MCP and private connector reach are **UNVERIFIED**. Defer it if stock production support and strict private-tailnet ingress are hard requirements. Tailscale alone also does not authenticate an agent profile, synchronize threads or prove low latency; retain per-bot application authorization and measure the whole remote path.

## What the repositories actually implement

1. **The neutral tools already exist, with historical names.** `browser-mcp.cjs` declares 14 tools before policy filtering: eight `cua_alans_way_*` browser/recording tools and six `workspace_computer_*` native-app tools. Its schemas include bounded observations, browser epochs, native generations, window IDs and `expect_host`; screenshots return MCP image blocks plus geometry. Names such as `browser.*` and `computer.*` describe a proposed vocabulary, not existing registered names. Hermes can normalize dots to underscores, so avoid assuming the client-visible spelling. [W2, H1]
2. **Router and transport do not need per-agent rewrites.** The agents repo already provides per-bot forced-command SSH setup and an HTTP front for the router. HTTP accepts POST/DELETE with JSON replies, has no GET event stream, rejects server-to-client requests, and strips elicitation/sampling/roots capabilities. JSON-only responses are permitted by Streamable HTTP; lack of SSE alone does not invalidate a basic tool server. Full client conformance is **UNVERIFIED**. [A2, A7, M1]
3. **Current bridge limits matter independently of client limits.** Requests are capped at **1 MiB**, **4 concurrent sessions**, **15 min idle**, and **5 min reply wait**. Those constants are not screenshot response-size limits. Each session gets the same configured router arguments; a shared token/listener is not a per-bot authorization mapping. [A2]
4. **Browser and desktop approvals differ.** Router browser commits require a `commit` summary and client form elicitation, refuse when unavailable, and bind approval to observed tab/page/epoch. Desktop launch/action opt-in is separate; the app asks unknown bots locally with a **40 s** prompt, temporary **30 min idle** grants, and denial cooldown. Trusted Hermes/overseer identities bypass that local prompt because their own client is expected to gate input. Broad desktop permission is not per-purchase browser approval. [A4, A8, W3]
5. **Leases and handoffs exist below MCP, not as a complete public tool family.** On Mac the app serializes launch/menu/action by bot identity with active-call exclusion and **20 s** idle expiry; competing input returns `desktop_busy` and retry timing. Reads can still expose shared desktop state, and the app constructs this lease only on Darwin: equivalent cross-agent Windows/Linux lease behavior is **UNVERIFIED**. Browser `action` supports claim/release. The app has a cross-host checkpoint/restore handoff function with `review_required`, while the router handles failover. No dedicated `lease.*` or `handoff.*` tools appear in the inspected MCP tool list. [W2, W4, W5]
6. **Hermes has extra adapter behavior.** The provider starts its own router with desktop input enabled, converts native controls into Hermes computer-use observations, attaches screenshots when needed, and waits up to 30 s for desktop contention. It registers only when Hermes exposes its provider API. Removing it would discard behavior that raw MCP clients do not automatically inherit. [A5]
7. **A prompt profile cannot replace runtime hooks.** Current voice reads per-plugin state and transforms output; proactivity depends on gateway session binding, scheduling and `ctx.inject_message`. A shared instruction file can communicate voice and limits, but cannot itself watch inactivity, deliver messages or reproduce those transformations. [A1, A6]

The sibling remote-agent guide says the bridge is still being finished, while pinned agents main already contains it; READMEs also describe older fallback behavior than the router source. Treat code as implementation evidence and those guides as historical reports; neither proves an installed production deployment or successful Grok lid-close continuation. [A2, A9, W1, W7]

## Minimum common tool contract (proposal)

Keep the current tool names for compatibility. Use `browser.*`, `computer.*`, `lease.*` and `handoff.*` as conceptual groups first; aliases or renames are separate implementation decisions. MCP supports named tools, object schemas, text/image content and structured results, but does not mandate an agent's approval UI or a universal tool-count limit. [M2]

| Group | Minimum contract | Reuse / required gap |
| --- | --- | --- |
| Discovery/session | `initialize`, `tools/list`, `tools/call`; authenticated principal maps to a fixed bot ID. Report host, capabilities and supported approval path. Do not take authoritative identity/trust from model arguments. | Reuse router and `--bot-id`; a multi-bot HTTP listener needs credential-to-bot mapping. Current fixed-bot listeners are a smaller interim option. [A2, A7] |
| `browser.*` | status/tabs/open/snapshot/screenshot/action/close; target tab and current epoch; refs from current observation; bounded text; errors distinguish stale state, human hold and uncertain execution. | Existing tools largely cover this. Preserve names and failover semantics. [W2] |
| `computer.*` | apps/launch/snapshot/screenshot/menu/action; bind actions to observed host, PID, window and generation; return changed/removed state or fresh observation. Screen/image geometry must say how pixels map to input coordinates. | Existing shared tools supply these; do not require Hermes element numbering. [W2, A5] |
| `lease.*` | Expose current holder, acquisition result and `retryAfter`; exclusive input, human priority, bounded idle expiry. Release must not grant another bot permission or interrupt a still-running input. | Mac enforcement exists; an explicit public status/release contract needs design and verification; the required targets here are the local Mac and configured VM. [W4] |
| `handoff.*` | Distinguish human claim/release, host continuation, and agent-to-agent reassignment. Return source/destination identity and tab IDs, host, fresh epoch/generation, review status and verification result. Failed handoff must not imply success or replay uncertain input. | Reuse claim/release and checkpoint/restore. Explicit cross-agent reassignment and MCP handoff tools are missing; do not promise browser session/login migration from checkpoint restoration. [W2, W5] |
| Results/errors | Short text summary plus structured fields; retain text JSON for clients ignoring `structuredContent`. Screenshots use `content: [{type:"image", data, mimeType}, {type:"text", text}]`, ideally one bounded image per result. Include stable error code, execution status and recovery advice. | Existing image/geometry shape fits. Structured error normalization and per-client image consumption require checks. [W2, M2] |
| Approval | Treat client permission, desktop grant and consequential-action consent as separate checks. Use negotiated form elicitation where available; otherwise refuse commits until an app-side, authenticated, action-bound consent flow exists. Never accept an approval invented by the model or retry uncertain input blindly. | Stdio has browser gating. HTTP needs a real bidirectional request path or shared app approval workflow; a profile's `trusted_tools` never substitutes for either. [A2, A4, W3] |

Recommended budgets, **not vendor guarantees**: retain the 14-tool surface initially, use root object schemas and short names, return text/controls before pixels, and configure clients above existing action budgets. Hermes setup already chooses 120 s; native batches document a shared 45 s budget, up to 25 steps. A **180 s client timeout** is a practical starting point, but long human approval waits need their own tested budget; increasing a timeout cannot fix an absent approval channel. The HTTP bridge still imposes its 5 min cap. [A3, W2, A2]

## Per-bot profile boundary (proposal)

Use one operator-owned, non-secret profile document as input to small adapters; no new profile format was implemented by this research. Minimum fields: stable bot ID/display name, voice instructions, proactivity enabled/quiet hours/timezone/delivery target, and allowed/trusted tool names. Keep credentials in each client's secret mechanism.

Render **instructions** into Hermes `SOUL.md`/skill, Grok Bot memory/skill, and conditional Duet skill/plugin when available. Apply **enforcement** to the authenticated server principal and client permissions, not only to prose. Set **proactivity** through a host runtime that can schedule and deliver: current Hermes plugin, Grok routines, or a separately verified integration. Do not infer unattended-turn capability from MCP connectivity. [H3, G4, G5, D2, A6]

This preserves one policy source without pretending every client loads the same file automatically. A client that cannot apply a profile field must report it unsupported rather than silently dropping a quiet-hours or approval rule. Shared desktop visibility, shared browser sign-ins and Grok account-wide connectors also mean per-bot profiles are not data-isolation sandboxes. [W1, W2, G1, H3]

## Gaps and recommendation

**Go-with-changes:** target production Hermes and Grok Bot through added tools and small profiles, keeping the existing Mac/browser drivers, workspace and VM viewer. Prefer a verified private-tailnet connector route for Grok; treat Funnel as a public-ingress exception needing a product decision. Keep Duet conditional: it exists but is a research preview, and its private networking/tool behavior does not yet satisfy the production-only core. Under a strict private-tailnet-only launch rule, Grok remains gated on verified connector reachability and Duet is deferred. The architecture is plausible; speed/accuracy, lid-close continuation, same-thread UI and proactive behavior still need acceptance evidence against all seven features. Do not fork agents or build independent drivers per agent.

Before claiming shared production support, resolve the hosted-ingress/Tailscale decision and run the seven acceptance checks above, then close these tool-level gaps:

1. **Fix HTTP approval coverage.** Carry negotiated server-to-client requests or supply a shared action-bound app approval path; keep current fail-closed browser behavior until then. Generic client permission cards do not supply the router's form response. [A2, A4]
2. **Bind bot identity to credentials.** Start with one restricted SSH key or fixed-bot bridge endpoint per bot; a single multiplexed endpoint later needs authenticated principal-to-profile mapping. Model-selected bot IDs and shared tokens must not inherit trusted Hermes privileges. [A2, A7, W3]
3. **Adapt profiles without promising runtime parity.** Keep voice text portable, enforce tool access outside prompts, and explicitly map scheduling/delivery and output transforms per client. [A1, A6]
4. **Complete ownership semantics.** Expose/verify lease status and human handback, prioritize laptop-to-VM continuation and human handback; cross-agent reassignment is deferred unless separately needed. The local Mac lease does not prove contention handling on the configured VM. [W4, W5]
5. **Run a narrow conformance exercise per client/version.** Verify auth refusal and bot isolation; list tools; read a page; receive one real screenshot; perform one harmless native action with correct host/window/generation; decline and accept an approval; hit stale-state and `desktop_busy`; release to the human; simulate failover without repeating uncertain input. For Grok and conditional Duet, record actual transport, private network reach, headers, image consumption and elicitation. This exercise was **not run**.

Open questions for Alex:

- Does “Tailscale for everything” require private-tailnet-only tool ingress, or permit authenticated Funnel ingress for a hosted connector?
- Which Grok Bot plan is production: does it expose the documented Enterprise Tailscale setup, and can its command connector reach the VM while the Mac sleeps?
- Should stock Grok chat remain in its own app, or must the same thread also appear in the workspace left pane? No verified thread-embedding interface was found.
- Is Duet preview acceptable as an experimental extra while production Hermes/Grok ship?
- What success/latency thresholds define Codex-level CUA, and may the benchmark drive Alex's Mac? No benchmark was run.

Skipped live clients, installed versions, deployment checks and runtime tests; this documentation-only change does not need application tests. Main risks: private hosted-MCP reachability, HTTP browser approval, production lid-close continuation and remote speed/accuracy are unproven; a profile cannot supply those guarantees.
